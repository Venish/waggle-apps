## 1. 결정 배경 (D14: RN 폐기)

교육앱 피벗(산책 → 교육 전문)으로 React Native를 유지할 이유가 사라졌고, 모바일웹 우선 전략으로 전환한다.

### 1.1 RN 폐기 이유

| 항목 | 내용 |
|---|---|
| 네이티브 요구 소멸 | RN + 네이티브 모듈(아키텍처_05)의 존재 이유는 **산책 GPS 트래킹**(장시간 백그라운드, 배터리, 위치 정확도)이었다. 산책 기능 제거(D1)로 백그라운드 GPS·네이버지도 네이티브 SDK·`packages/native-walk`가 모두 불필요해짐 |
| 개발 부담 | 에뮬레이터/시뮬레이터 기반 개발 사이클이 무겁다. 웹은 Chrome DevTools 모바일 뷰로 즉시 개발·디버깅 가능 |
| 디자인 제어 | 듀오링고식 커리큘럼 경로 UI 등 커스텀 디자인은 웹(CSS)이 RN보다 제어가 용이하고, admin-web과 Tailwind v4 + `@waggle/design-tokens`를 그대로 공유 가능 |
| 배포 민첩성 | 웹은 스토어 심사 없이 즉시 배포. shell은 껍데기만 유지하므로 앱 업데이트 빈도 최소화 |

### 1.2 타깃과 iOS 필수성

- 핵심 타깃: **20~30대 여성 반려인** → iPhone 점유율이 높아 **iOS 지원은 필수**
- 다만 iOS는 App Store 심사(특히 4.2 최소 기능성) 리스크가 있으므로 **2단계**로 진행: 모바일웹 + Android shell로 기능 검증 → 확정 후 iOS shell 출시

### 1.3 단계별 출시 전략

```
1단계: apps/mobile-web (Next.js)
        └─ 브라우저 단독으로 전체 기능 서비스 가능 (푸시 등 일부 제한)
        └─ apps/android-shell → Play 스토어 테스트 트랙 (내부/비공개 테스트)
2단계: apps/ios-shell → App Store 정식 출시 (기능 확정 후)
```

모바일웹 단독으로도 서비스가 성립해야 한다(D14). shell은 **푸시 + 스토어 존재감**을 위한 최소 래퍼다.

## 2. 전체 구성

```
apps/
├── mobile-web/       # Next.js 15 App Router — 서비스 본체 (app.waggle.app 가칭)
├── android-shell/    # Kotlin, WebView 래퍼 + FCM (1단계)
├── ios-shell/        # Swift, WKWebView 래퍼 + APNs (2단계)
├── admin-web/        # 기존 유지 (Next.js 15)
├── mobile-api/       # 기존 유지 — mobile-web이 호출하는 MAPI
└── ...
```

| 구성요소 | 기술 | 역할 |
|---|---|---|
| `apps/mobile-web` | Next.js 15 App Router, TypeScript strict, Tailwind CSS v4 | 모든 화면·비즈니스 UI. **모바일 우선 반응형**(기준 뷰포트 ~390px, max-width 컨테이너로 태블릿/데스크톱 대응) |
| `apps/android-shell` | Kotlin, AndroidX WebView | mobile-web 로드 + FCM 푸시 + 딥링크 라우팅 |
| `apps/ios-shell` | Swift, WKWebView | mobile-web 로드 + APNs + 네이티브 탭바·알림설정 (심사 대응) |

### 2.1 admin-web과의 공유

- **Tailwind CSS v4 + `@waggle/design-tokens`** 공유: 색/간격/타이포 토큰을 두 웹 앱이 동일하게 사용
- `@waggle/dto`(Zod 스키마), `@waggle/deeplinks`(라우트 정의) 공유
- `@waggle/ui-web`(ShadCN 확장)은 관리자 성향 컴포넌트가 많으므로 mobile-web은 선별 사용, 소비자용 컴포넌트는 mobile-web 내부에 별도 구축

### 2.2 삭제 대상 (D23)

`apps/mobile-app`(RN), `apps/poc-walk`, `packages/native-walk` — 디렉터리 삭제. 관련 문서(아키텍처_05·06·07, 개발계획_03)는 폐기 배너 처리 완료.

## 3. mobile-web 상세

### 3.1 라우팅 구조 (App Router)

```
app/
├── (onboarding)/
│   ├── welcome/              # 시작 화면, 소셜 로그인
│   ├── dog-profile/          # 강아지 프로필 등록 (이름·견종·월령·성별·중성화·체중)
│   ├── survey/[step]/        # 설문 7문항 (객관식·비분기, D17)
│   ├── recommendation/       # 룰 기반 태그 매칭 결과 → 커리큘럼 추천
│   └── level-test/           # 레벨테스트 (선택, 경험자용)
├── (main)/                   # 하단 탭 레이아웃
│   ├── home/                 # 홈 = 듀오링고식 커리큘럼 경로 UI (유닛/레슨 노드, 순차 잠금)
│   ├── daily/                # 일상기록 (캘린더 뷰, 접종·산책유무·사진·자유기록)
│   ├── shop/                 # 포인트샵 (실물/문의권/프리미엄)
│   ├── qna/                  # 훈련사 영상 Q&A (목록·작성·답변 확인)
│   └── my/                   # 마이 (강아지 관리, 포인트 내역, 배지/학년, 설정)
├── lesson/[lessonId]/
│   ├── watch/                # 레슨 플레이어 (YouTube IFrame)
│   ├── practice/             # 실습 자가체크 체크리스트
│   └── quiz/                 # 최종퀴즈 (4지선다 3~5문항, D18)
├── points/
│   ├── recharge/             # 포인트 충전 — 채널 분기 지점 (§6)
│   └── history/              # 원장 내역 (적립/사용/소멸 예정)
└── api/                      # Route Handler는 최소화 — 데이터는 MAPI 직접 호출
```

- 레슨 플로우(`watch → practice → quiz`)는 탭 밖 전체화면 스택으로 분리해 몰입 유지
- 온보딩 완료 여부·강아지 등록 여부에 따라 미들웨어에서 리다이렉트

### 3.2 YouTube IFrame Player API 연동 (D6·D19)

- unlisted 영상을 **IFrame Player API**로 임베드. 관리자 CMS에는 videoId만 등록
- **시청완료 판정: 95% 이상 시청, 배속 허용**(D19)
  - `onStateChange` + 주기 폴링(`getCurrentTime`/`getDuration`)으로 실제 시청 구간을 클라이언트에서 누적 추적 (단순 탐색 점프로 95% 도달 방지 — 시청 구간 세그먼트 합산)
  - 배속(`playbackRate`)은 진도 인정에 영향 없음
  - 판정은 클라이언트, **기록은 서버**: 완료 시 MAPI에 진도 이벤트 전송 → `LessonProgress` 갱신 → `point-settler` 경유 최초 1회 적립(D7)
- **videoId 노출 최소화**: 페이지 소스에 직접 렌더하지 않고, 레슨 진입 시 인증된 API로 조회해 플레이어에 주입. (완전 은닉은 불가 — YouTube 의존 리스크는 스펙 §9 참조, 장기적으로 S3+HLS 전환 경로 유지)
- 오프라인 시청 불가 — 명시적 한계로 수용

### 3.3 상태관리·스토리지

| 구분 | RN 시절 | mobile-web |
|---|---|---|
| 서버 상태 | TanStack Query v5 | **동일 유지** |
| 전역 UI 상태 | Zustand | Zustand (최소한으로) |
| 로컬 스토리지 | MMKV | **웹 스토리지로 대체** — localStorage(경량 설정), IndexedDB(진도 캐시 등 구조화 데이터) |

- MMKV 산책 버퍼링은 제거. 오프라인 대비는 **진도 이벤트 큐잉** 수준으로 축소: 시청완료/실습체크 이벤트를 IndexedDB에 적재 후 네트워크 복구 시 재전송 (TanStack Query mutation 재시도와 병행)
- 낙관적 UI(포인트 적립 팝업 등) 원칙은 유지

### 3.4 인증 (기존 JWT 재사용)

- 기존 체계 유지: Access Token 15분 / Refresh Token 30일, 소셜 로그인
- **웹 채널 전략**: Refresh Token은 `HttpOnly; Secure; SameSite=Lax` 쿠키, Access Token은 메모리 보관(재발급으로 복구). XSS로 인한 토큰 탈취 면적 최소화
- **웹뷰(shell) 채널**: WebView/WKWebView의 쿠키 저장소를 그대로 사용 — 동일 도메인이므로 웹과 동일 플로우로 동작. shell은 인증에 관여하지 않는다(네이티브에 토큰 보관 금지)
- 소셜 로그인 리다이렉트는 웹뷰 내에서 완결 (외부 브라우저 이탈 없이 처리, 각 IdP의 웹뷰 정책 확인 필요 — Google은 시스템 브라우저/Custom Tabs 요구 가능성 있어 구현 시 검증)

### 3.5 Q&A 영상 업로드

- `<input type="file" accept="video/*" capture="environment">` 로 촬영/앨범 선택 — **네이티브 브릿지 불필요**, iOS Safari·Android WebView 모두 지원
- 업로드: presigned URL로 S3 직접 업로드 → 완료 콜백 → `video-postprocess` 큐(Q&A 영상 전용으로 축소 유지)
- 대용량 대비: 업로드 진행률 표시, 길이 제한(≤N분, 스펙 §4.7) 클라이언트 1차 검증

## 4. Android Shell 상세 (apps/android-shell)

### 4.1 WebView 설정

- 단일 Activity + WebView 전체화면. `javaScriptEnabled`, `domStorageEnabled` 활성화
- mobile-web 도메인만 WebView 내 로드 허용 — 외부 링크는 Custom Tabs/기본 브라우저로 위임
- 파일 선택(`onShowFileChooser`) 및 카메라 권한 위임 구현 (Q&A 업로드용)
- 쿠키 유지: `CookieManager` 영속화 (로그인 세션 유지)

### 4.2 JS Bridge 인터페이스

`@JavascriptInterface`로 최소한의 브릿지만 노출. mobile-web은 `window.WaggleBridge` 존재 여부로 채널을 식별한다.

```
WaggleBridge (android → web 주입)
├── getChannel(): "android-shell"            # 채널 식별 (§6 IAP 분기에 사용)
├── getPushToken(): string | null           # FCM 토큰 전달 → web이 MAPI 토큰등록 API 호출
├── openNotificationSettings(): void        # OS 알림 설정 화면 열기 (푸시 거부 시 유도)
└── getAppVersion(): string                 # shell 버전 (강제 업데이트 판단용)
```

- 역방향(native → web)은 URL 로드 파라미터·`evaluateJavascript` 콜백으로 최소화
- 브릿지에 결제·인증 관련 기능은 두지 않는다

### 4.3 FCM 푸시 → 딥링크 라우팅

1. `FirebaseMessagingService`에서 수신 (데일리 리마인드, 포인트 소멸 예고, Q&A 답변 도착 등 — `notification-dispatcher` 발송)
2. 알림 페이로드에 `@waggle/deeplinks` 기반 경로 포함 (예: `/qna/{inquiryId}`, `/home`)
3. 알림 탭 → Activity 인텐트 → WebView가 해당 경로 로드
4. 토큰 갱신(`onNewToken`) 시 브릿지 경유로 web에 전달 → MAPI 토큰 등록 API 재호출

### 4.4 출시

- **Play 스토어 테스트 트랙**(내부 테스트 → 비공개 테스트) 배포로 실사용 검증
- shell 자체 업데이트는 드묾(브릿지/푸시 변경 시에만) — 기능 배포는 전부 웹 배포로 처리

## 5. iOS Shell 계획 (apps/ios-shell, 2단계)

- **WKWebView + APNs**: Android shell과 동일한 브릿지 계약(`window.WaggleBridge`, `getChannel(): "ios-shell"`)을 `WKScriptMessageHandler`로 구현
- **심사 가이드라인 4.2(최소 기능성) 대응** — "웹사이트 래퍼" 리젝 방지를 위해 네이티브 요소 포함:
  - **네이티브 탭바**(홈/일상기록/샵/Q&A/마이) — 탭 전환은 네이티브, 콘텐츠는 WebView
  - **네이티브 알림 설정 화면** (푸시 카테고리별 on/off, 리마인드 시간)
  - 앱 아이콘 뱃지, 햅틱 피드백 등 소소한 네이티브 통합
- APNs 토큰 등록·딥링크 라우팅은 Android와 동일 패턴
- 출시 시점: mobile-web + Android shell로 기능 확정 후. IAP(§6)는 iOS 출시의 선행 조건

## 6. 채널 분기와 IAP (D15)

### 6.1 채널 감지

| 채널 | 감지 방법 |
|---|---|
| 브라우저 (모바일웹) | `window.WaggleBridge` 없음 |
| Android shell | 브릿지 `getChannel() === "android-shell"` (+ 보조: WebView UA 커스텀 suffix `WaggleShell/1.0`) |
| iOS shell | 브릿지 `getChannel() === "ios-shell"` |

브릿지를 1차 신뢰하고 UA는 보조 수단으로만 사용 (UA는 위·변조 가능).

### 6.2 충전 화면 분기 (D15)

- 상품(포인트샵)은 **포인트 단일 가격** — 채널 무관 동일
- **포인트 충전 가격만 채널별 차등**: 웹 10,000원=10,000P vs IAP 12,000원=10,000P (수수료 반영, 값은 관리자 정책 설정 D16)

| 채널 | 충전 화면 노출 |
|---|---|
| 브라우저 | **PortOne**(PG: 카드/간편결제) 패키지 |
| Android/iOS shell | **IAP 패키지만** 노출. PortOne 결제창은 웹뷰에서 절대 노출 금지 |

- **스티어링 금지**: 앱(shell) 내에서 "웹에서 충전하면 더 저렴" 등 웹 가격 노출·유도 문구 일절 금지 (스토어 정책 위반)
- 한국 제3자 결제 옵션은 수수료(~26%)로 실익이 없어 채택하지 않음 (스펙 §9)

### 6.3 IAP 처리 흐름

1. shell이 스토어 결제 UI 실행 (충전 화면에서 브릿지 경유 트리거 — 브릿지에 `requestIAP(productId)` 추가는 IAP 구현 시점에 확장)
2. 결제 완료 → 영수증(구매 토큰)을 MAPI `recharge` 모듈로 전송
3. **서버 영수증 검증 필수**: Google Play Developer API / App Store Server API로 검증 후 `PointRecharge` 기록 + 포인트 지급 (`point-settler` 경유, 단일 트랜잭션 원칙)
4. 중복 지급 방지: 구매 토큰 유니크 제약, 검증 전 지급 금지
5. PortOne(웹)은 기존 결정대로 webhook으로 동일 `recharge` 모듈에서 처리 — 원장에는 충전분/적립분 구분 기록

## 7. 푸시 아키텍처

| 채널 | 수단 | 도달 전략 |
|---|---|---|
| 브라우저 (Android Chrome 등) | 웹푸시 (Push API + Service Worker) | 제한적 지원. iOS Safari는 홈화면 추가(PWA) 시에만 가능 → **기대치 낮게, 보조 수단** |
| Android shell | FCM | 주력. 데일리 리마인드·소멸 예고·Q&A 답변 알림 |
| iOS shell | APNs | 2단계 주력 |

- **토큰 등록 API** (MAPI): `POST /notifications/push-tokens` — `{ token, channel: "fcm" | "apns" | "webpush", deviceInfo }`. 사용자당 다중 기기 허용, 만료/실패 토큰은 발송 실패 시 정리
- `notification-dispatcher` 워커가 채널별 어댑터(FCM/APNs/WebPush)로 발송 — 사용자별 활성 토큰 채널을 조회해 라우팅
- 푸시 불가 사용자(순수 브라우저)는 인앱 알림함 + (2차) 알림톡 등 대체 채널 검토
- shell 미설치 브라우저 사용자에게는 데일리 리마인드 가치를 근거로 앱 설치를 유도 (푸시가 shell의 핵심 존재 이유)

## 8. 향후: 위치기반 커뮤니티 (2차 이후)

- 동네 펫샵·동물병원·애견카페 검색 + 사용자 커뮤니케이션 (상세 기획 미정, 스펙 §10-6)
- **네이버맵 JS API v3**를 mobile-web에서 직접 사용 — 네이티브 SDK·브릿지 **불필요** (개발계획_03 PoC가 폐기된 이유 중 하나)
- 현재 위치는 브라우저 **Geolocation API** (`navigator.geolocation`) 사용 — 웹뷰에서는 shell이 위치 권한 위임(`onGeolocationPermissionsShowPrompt` 등) 구현 필요
- 백그라운드 위치·경로 트래킹은 하지 않는다 (산책 기능 제거로 요구사항 소멸). 지도는 항상 포그라운드 조회용

## 9. 개발/배포

### 9.1 개발 환경

- **에뮬레이터 불필요**: Chrome DevTools 디바이스 모드로 개발, 실기기 확인은 로컬 네트워크 접속 또는 원격 디버깅(`chrome://inspect`)
- `pnpm --filter mobile-web dev` 로 즉시 기동 — RN Metro/Xcode/Gradle 빌드 사이클 제거
- shell 개발은 브릿지·푸시 변경 시에만 필요 (Android Studio / Xcode)

### 9.2 배포

- **Vercel 미사용** — 기존 인프라 유지: mobile-web을 Docker 이미지로 빌드(standalone output) → `infra/compose` docker-compose에 서비스 추가 → Nginx 리버스 프록시로 라우팅
- CI/CD: 기존 GitHub Actions → webhook receiver 흐름 그대로 (staging 자동, prod 수동 승인)
- shell 배포: Android는 Play 테스트 트랙 → 정식, iOS는 TestFlight → App Store (2단계). 웹 배포와 완전 분리 — 기능 변경의 대부분은 웹 배포만으로 완결

### 9.3 turbo/모노레포 반영

- `apps/mobile-web`은 기존 Turborepo 파이프라인(`dev`/`build`/`test`/`lint`)에 편입
- `android-shell`/`ios-shell`은 JS 파이프라인 밖(네이티브 빌드) — turbo 태스크 대상에서 제외하고 각자 빌드 체계 유지
