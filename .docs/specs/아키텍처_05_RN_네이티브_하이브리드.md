## 1. 배경

Waggle의 핵심 사용자 흐름은 "산책 → 포인트 → 포인트샵" 순환이다. 이 흐름의 입구인 **산책 트래킹**은 다음 네 가지 품질 요소를 동시에 만족해야 한다.

1. **장시간 백그라운드 유지** (iOS 화면 잠김 30분+ 가정)
2. **GPS 정확도**(터널·빌딩가 오차 최소화)
3. **배터리 효율**(30분 산책 시 앱 단독 소모 5% 이내 목표)
4. **앱 프로세스 종료 후 복원**(Android OS 메모리 회수 대비)

순수 React Native로 이 네 가지를 모두 맞추는 것은 구조적 한계가 있다. 본 문서는 **네이티브 코어 + RN 쉘** 하이브리드 아키텍처를 제안하고, 현재 아키텍처 대비 장단점을 정리한다.

## 2. 순수 RN 접근의 병목

| 병목 | 증상 | 원인 |
|---|---|---|
| Bridge 오버헤드 | 1Hz GPS 업데이트 시 JS 스레드 압박, FPS 저하 | 위치 → Bridge 직렬화 → JS setState → re-render |
| iOS 백그라운드 정지 | 화면 잠금 시 기록 중단 | iOS는 JS 타이머·네트워크를 suspend |
| Android 프로세스 kill | OS가 메모리 회수 시 세션 소실 | Foreground Service가 없는 JS 프로세스는 중단 대상 |
| 긴 polyline 렌더 | 5,000+ 포인트에서 스크롤 랙 | JS에서 좌표 배열 전달 → 네이티브 재변환 |
| 센서 fusion 부재 | 차량·지하 이동 오탐 | JS로 실시간 센서 퓨전 구현 부담 |
| 배터리 | 30분 사용 시 8–12% | JS 스레드 + Bridge 상시 활성 |

유료 SDK(`react-native-background-geolocation`)로 일부 우회 가능하나, **Bridge는 그대로**이며 네이버지도 RN wrapper의 렌더 성능도 네이티브 SDK 대비 낮다.

## 3. 제안 아키텍처 — "네이티브 코어 + RN 쉘"

### 3.1 개념

산책 트래킹의 **런타임과 Map 렌더**를 네이티브로 옮기고, UI 껍데기·비-산책 화면·서버 통신은 RN 그대로 유지한다.

```
┌─────────────────────────────────────────────────────────────┐
│                        RN Layer (UI)                        │
│   홈·수첩·교육·미션·포인트샵·마이 (그대로 RN)                       │
│                                                             │
│   산책 탭 화면 껍데기 (시작/종료 버튼, 요약, 목록)                     │
│   └ <WalkMapView />       ← Fabric Native Component           │
│   └ useWalkTracker()      ← TurboModule 훅                    │
└──────────────┬──────────────────────────┬───────────────────┘
               │ JSI (sync, low-latency)  │ Fabric (native view)
               ▼                          ▼
┌─────────────────────────────────────────────────────────────┐
│                  Native Core (iOS / Android)                │
│   WalkTrackingService                                       │
│    - iOS : CLLocationManager + Background Modes             │
│    - AOS : ForegroundService + FusedLocationProvider        │
│   LocationFilter  (Kalman + 속도 이상치 + Douglas-Peucker)    │
│   SessionStore    (Core Data / Room, 오프라인 버퍼)             │
│   SensorFusion    (가속도계 → 정지 감지, 자동 일시정지)             │
│   WalkMapView     (네이버지도 네이티브 SDK 직접 사용)              │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 레이어 책임

- **RN이 담당**: 화면 라우팅, 통계 표시(거리·시간 숫자), 산책 요약·기록 목록, 서버 업로드, 포인트 애니메이션
- **네이티브가 담당**: GPS 수집·필터링·저장, 포그라운드 알림, Map 렌더, 세션 생명주기, 앱 kill 후 복원
- **경계 규칙**: 원시 좌표는 **네이티브 안에서만** 흐름. RN에는 **요약 통계와 상태 전이 이벤트만** 전달.

### 3.3 통합 방식 비교

| | A. RN UI + 네이티브 모듈 | **B. 네이티브 코어 + Fabric View 임베드** ⭐ | C. 네이티브 스크린 전환 |
|---|---|---|---|
| 개념 | 기능만 네이티브, Map도 RN wrapper | 산책 탭은 RN, Map·세션은 네이티브 | 산책 중 화면만 네이티브 ViewController/Activity |
| 성능 이득 | 중 | **상** | 최상 |
| 개발 공수 | 중 | 중–상 | 상 |
| 코드 공유 | 좋음 | 좋음 | 제한적 |
| 디자인 일관성 | 쉬움 | 쉬움 | 두 번 구현 |
| RN 업그레이드 | 쉬움 | 중 (Codegen 재생성) | 중 |
| 권장 사유 | Map wrapper 성능 한계 | **Bridge 회피 + UI 일관성** | 과잉 엔지니어링 |

**채택: 옵션 B**

## 4. 기술 선택

### 4.1 필수 전제 — New Architecture ON

RN 0.76+에서 **Fabric + TurboModules + JSI + Codegen**을 반드시 활성화한다. 그래야 본 설계의 이점이 구현된다.

- **JSI HostObject / TurboModule EventEmitter**: 네이티브 → JS 고주파 이벤트 전달에서 Bridge 직렬화 회피
- **Fabric Native Component**: Map 뷰를 네이티브 구현체로 노출 (iOS `RCTViewComponentView`, Android `ViewManager`)
- **Codegen**: TS 스펙을 단일 진실로 두고 네이티브 인터페이스 자동 생성

### 4.2 산책 네이티브 모듈 구조

```
apps/mobile-app/
├── specs/
│   └── NativeWalkTracker.ts          ← Codegen 입력 (단일 진실)
│
├── ios/Waggle/Walk/
│   ├── WalkTrackingManager.swift     ← CLLocationManager 래퍼
│   ├── LocationFilter.swift          ← Kalman + Douglas-Peucker
│   ├── WalkSessionStore.swift        ← Core Data
│   ├── SensorFusion.swift            ← CMMotionManager
│   ├── WalkTrackerModule.mm          ← TurboModule 바인딩
│   └── WalkMapView.swift             ← Fabric Component (네이버지도 iOS SDK)
│
├── android/app/src/main/java/app/waggle/walk/
│   ├── WalkTrackingService.kt        ← ForegroundService
│   ├── FusedLocationSource.kt        ← Google Play Fused Location
│   ├── LocationFilter.kt
│   ├── WalkSessionDao.kt             ← Room
│   ├── SensorFusion.kt
│   ├── WalkTrackerModule.kt          ← TurboModule
│   └── WalkMapView.kt                ← Fabric Component (네이버지도 Android SDK)
│
└── src/features/walk/                ← 순수 RN UI
    ├── WalkStartScreen.tsx
    ├── WalkInProgressScreen.tsx      ← <NativeWalkMap /> 임베드
    ├── WalkSummaryScreen.tsx
    ├── WalkListScreen.tsx
    └── useWalkTracker.ts             ← TurboModule 훅
```

### 4.3 TypeScript 스펙 예시

```typescript
// specs/NativeWalkTracker.ts  — Codegen이 네이티브 인터페이스 생성
import type { TurboModule } from 'react-native';

export interface Spec extends TurboModule {
  start(dogId: string, config: Object): Promise<string>;  // -> sessionId
  pause(): Promise<void>;
  resume(): Promise<void>;
  stop(): Promise<Object>;                                // -> summary
  getCurrentSession(): Promise<Object | null>;
  addListener(eventName: 'stats' | 'state'): void;
  removeListeners(count: number): void;
}
```

### 4.4 이벤트 throttling 규칙

| 이벤트 | 네이티브 내부 주기 | JS로 전달 주기 | 이유 |
|---|---|---|---|
| 원시 GPS | 1초 | 전달 안 함 | 전부 네이티브 DB로 저장 |
| 실시간 통계(거리·속도) | 1초 | **3초** | UI는 3초면 충분, Bridge 압력 1/3 |
| 상태 전이(시작/일시정지/종료) | 즉시 | 즉시 | 사용자 인지 필요 |
| 종료 요약 | 1회 | 1회 | 최종 결과 |

### 4.5 백그라운드 구성

- **iOS**
  - `Info.plist`: `UIBackgroundModes = location, fetch`
  - `CLLocationManager.allowsBackgroundLocationUpdates = true`
  - 필요시 "Always" 권한 요청 (심사에서 이유 명확히)
  - 산책 중 `MKMapView`/`NMFMapView`는 네이티브 그대로
- **Android**
  - `ForegroundService` + `FOREGROUND_SERVICE_LOCATION` 권한
  - 고정 알림(`NotificationCompat` LowImportance + ongoing)
  - 재부팅 대비 `BOOT_COMPLETED` → 세션 복원 훅
  - `WorkManager`로 완료되지 않은 세션 플러시 잡 등록

### 4.6 오프라인·복원 전략

| 상황 | 처리 |
|---|---|
| 네트워크 끊김 | 네이티브 SQLite에 포인트 계속 적재 |
| 앱 포그라운드 복귀 | TurboModule이 즉시 현재 세션 리턴, UI 재구성 |
| 앱 kill (Android) | Foreground Service가 계속 수집, 다음 앱 기동 시 `getCurrentSession` 반환 |
| OS 재부팅 | `BOOT_COMPLETED` 리시버가 미완료 세션 플래그만 세팅 → 사용자 앱 진입 시 "종료하시겠습니까?" 프롬프트 |
| 서버 업로드 | 산책 종료 시점에 RN이 한 번에 업로드. 실패 시 MMKV 큐 + 지수 백오프 |

## 5. 성능 비교 (순수 RN vs 하이브리드)

| 지표 | 순수 RN | 네이티브 코어 + RN 쉘 | 개선폭 |
|---|---|---|---|
| GPS 업데이트 → UI 반영 지연 | 30–80ms | 5–15ms (JSI) · 3초 throttle | 40–60% 감소 |
| iOS 백그라운드 유지율(30분 화면 잠김) | 40–70% | **99%+** | 결정적 |
| Android 앱 kill 후 세션 복원 | 불가 | **가능** | 결정적 |
| 30분 산책 앱 단독 배터리 | 8–12% | 4–6% | 약 40% 감소 |
| polyline 5,000포인트 FPS | 35–45 | **55–60** | 체감 큼 |
| 거리 측정 오차(도심·터널) | 10–15% | 5–8% | 절반 |
| 앱 콜드 스타트 | 기준 | +100–200ms | 약간 악화 |
| 앱 번들 크기 | 기준 | +3–6MB | 허용 범위 |

**결정적 차이는 ① 백그라운드 유지율 ② 앱 kill 복원** 두 항목이다. 나머지는 "좋아지는" 수준이지만, 이 둘은 사용자 신뢰를 좌우하는 품질 지표이다.

## 6. 장점·단점

### 장점
- OS 수준 백그라운드 보장 (iOS background location, Android foreground service)
- Bridge 오버헤드 회피 — 원시 GPS는 네이티브 내부에서만 흐름
- 네이버지도 네이티브 SDK의 GPU 가속 맵 렌더링 완전 활용
- 배터리 절감 — JS 스레드 유휴, OS geofencing으로 정지 시 자동 샘플링 감소
- 오프라인 견고성 — 네이티브 DB에 즉시 저장
- 센서 퓨전으로 차량 이동·엘리베이터 등 오탐 감소
- 네이버지도 API 키·시크릿을 네이티브에 보관(JS 번들 디컴파일 방지)

### 단점
- 산책 모듈 한정 개발 공수 +30–50%
- iOS·Android 네이티브 개발자 각 1명 이상 필요 (파트타임 가능)
- 네이티브 로직 수정 시 OTA(Shorebird/CodePush) 불가 → 스토어 심사
- 디버깅 복잡도 증가 (Xcode / Android Studio / Flipper 병행)
- RN 업그레이드 시 Codegen 스펙 호환성 점검 필요
- 초기 스프린트 1주 추가 소요

### 리스크 / 회피
| 리스크 | 회피책 |
|---|---|
| 네이버지도 네이티브 SDK ↔ RN New Arch 호환성 | Phase 0에서 **양 플랫폼 PoC 앱** 1–2일 제작 후 확정 |
| iOS 리뷰의 "Always" 위치 권한 거절 | 앱 설명·권한 문구에 "산책 거리 측정" 명시. 필요시 "When-in-use" 우선, 백그라운드 업데이트만 활성화 |
| JSI·Codegen 학습 곡선 | 공식 템플릿 + `react-native-builder-bob`, 샘플 모듈 먼저 완성 |
| 네이티브 버그의 앱 전체 영향 | 산책 모듈을 **독립 라이브러리**(`@waggle/native-walk`)로 분리, 의존성 격리 |
| 네이티브 인력 공백 | 기능 플래그로 유료 RN SDK fallback 경로 유지(비상용) |

## 8. 권고

**네이티브 하이브리드(옵션 B) 채택을 권고한다.**

- 산책 트래킹은 waggle의 핵심 가치 전달 지점이며, 품질 실패 시 "기록이 반만 남는 경험"이 유저 이탈 1순위 요인이 된다.
- 순수 RN의 한계는 **엔지니어링 노력으로 회피 불가**한 OS 수준 제약(iOS JS suspend, Android process kill)이 본질이다.
- 타겟 영역이 산책 모듈로 한정되어 **전체 코드 공유율 85%+**를 유지할 수 있다.
- Phase 5 확장 기능(운동 챌린지·실시간 경로 공유)에도 그대로 재사용되는 기반 자산이 된다.

### 하지 않아도 되는 조건
- 팀에 iOS·Android 네이티브 역량이 전무하고, 3개월 내 절대적 출시 데드라인 → MVP는 유료 SDK(`react-native-background-geolocation` + 네이버지도 wrapper)로 시작, Phase 2에서 교체. **단, 교체 비용이 처음부터 만드는 비용보다 크다.**

## 10. ADR 요약 (결정 기록)
