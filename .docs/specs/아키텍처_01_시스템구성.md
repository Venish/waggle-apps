작성일: 2026-04-16
버전: v0.1 (초안, 리뷰 대상)

## 1. 서비스 개요

Waggle은 반려견의 라이프 로그(강아지 수첩) + 생애주기 교육 + 산책 기록 + 미션/리워드 + 포인트샵을 통합한 행동 기반 리워드 서비스다.

핵심 가치 흐름:

```
산책 / 교육 / 미션 달성 → 포인트 적립 → 포인트샵에서 소비
```

이 흐름을 안정적으로 지원하기 위해 **모바일 앱 백엔드(MAPI)**와 **관리자 백엔드(AAPI)**를 물리적으로 분리하고, 공용 데이터 계층(PostgreSQL)과 공용 도메인 로직은 모노레포 구조 안에서 공유한다.

## 3. 시스템 구성요소

### 3.1 클라이언트 (프론트엔드)

| 구성 | 기술 | 역할 |
|---|---|---|
| **모바일 앱** | React Native + 네이티브 하이브리드 (옵션 B 확정) | 대부분의 화면은 RN, **산책 트래킹 코어·Map·위치 서비스는 iOS(Swift)/Android(Kotlin) 네이티브로 직접 구현**. 상세는 `아키텍처_05_RN_네이티브_하이브리드.md` |
| **모바일 웹 (선택)** | Next.js 15 (App Router) | 웹 공유 링크, 랜딩페이지, PWA 대체 창구 (2차) |
| **관리자 웹** | Next.js 15 + TypeScript + ShadCN/UI + TanStack Query | 운영/CS/기획팀용 관리 콘솔 |

> **결정사항 1**: 모바일 앱은 React Native를 주축으로 하되, **산책 트래킹 모듈(위치·Map·세션 저장)은 iOS/Android 네이티브**로 구현하는 하이브리드(옵션 B)를 채택. 네이버지도는 **네이티브 SDK를 직접 사용**하고 Fabric Native Component로 RN에 노출. 전체 코드 공유율 85%+ 유지.
> **결정사항 2**: 모바일웹은 MVP 범위에서 제외. v1 이후 랜딩/공유 링크 용도로 추가. (필요시 RN Web으로 재사용 검토)

### 3.2 백엔드

두 개의 독립 NestJS 애플리케이션으로 구성한다. 동일 모노레포 안에 배치하여 도메인 로직과 Prisma 스키마를 공유한다.

| 구성 | 엔드포인트 예시 | 용도 |
|---|---|---|
| **MAPI (Mobile API)** | `api.waggle.app` | 앱에서 호출. 사용자 인증, 반려견, 산책, 교육, 미션, 포인트, 포인트샵, 알림 |
| **AAPI (Admin API)** | `admin-api.waggle.app` (IP 화이트리스트) | 관리자 콘솔 전용. 콘텐츠 CRUD, 운영 통계, 환불/포인트 조정 |

공통 원칙:
- **NestJS + Fastify 어댑터** (Express 대비 처리량/메모리 이점)
- **Prisma 6.x** (PostgreSQL 드라이버, 단일 스키마 공유)
- **Zod** 또는 **class-validator + class-transformer** (DTO 검증)
- **@nestjs/swagger** 기반 OpenAPI 자동 문서화
- **Pino** 로거 (Fastify 기본 로거)

### 3.3 데이터/인프라 계층

| 구성 | 기술 | 용도 |
|---|---|---|
| **RDB** | PostgreSQL 16 | 사용자, 반려견, 수첩, 산책, 교육, 미션, 포인트, 주문 |
| **공간 인덱스** | PostGIS 확장 | 산책 경로 Polyline 저장 및 거리 계산, 지역 기반 알림 |
| **캐시/세션/큐 브로커** | Redis 7 | Refresh token blacklist, 상품 상세 캐시, BullMQ 브로커 |
| **작업 큐** | BullMQ | 미션 검증, 알림 발송, 영상 후처리, 주문 정산 |
| **오브젝트 스토리지** | AWS S3 또는 NCP Object Storage | 프로필/산책 사진, 상품 이미지, 교육 영상 원본 |
| **CDN** | CloudFront / NCP CDN+ | 이미지/영상 전송 |
| **영상 스트리밍** | S3 + HLS (MediaConvert) 또는 Mux (선택) | 교육 영상 adaptive bitrate 스트리밍 |

> **결정사항 3**: MVP는 **S3 + 정적 HLS 프리셋**으로 시작. 영상 수/트래픽 증가 시 MediaConvert 또는 Mux로 전환.

## 4. 네트워크 / 보안 구성

### 4.1 서브 도메인 분리

```
app.waggle.app            ← (향후) 모바일 웹
api.waggle.app            ← MAPI (모바일 전용)
admin.waggle.app          ← 관리자 웹
admin-api.waggle.app      ← AAPI (IP 화이트리스트)
cdn.waggle.app            ← 정적/미디어 CDN
```

### 4.2 인증 방식

- **모바일**: JWT(Access 15분) + Refresh Token(30일, Redis 블랙리스트 관리) + 디바이스 바인딩(fingerprint)
- **관리자**: JWT + RBAC(관리자 역할: SUPER_ADMIN / OPERATOR / CS / VIEWER) + 관리자 IP 화이트리스트 + 2FA(TOTP, 2차)
- **소셜 로그인**: OAuth → 자체 JWT 발급 (소셜 토큰은 서버 보관 금지, 최초 프로필만 사용)

### 4.3 HTTPS / TLS

- 모든 트래픽 TLS 1.2+ 강제 (HSTS)
- 자체 구축 시 Let's Encrypt + Nginx, AWS 시 ACM + ALB/CloudFront
- API → DB 접근은 VPC 내부망 only

### 4.4 비밀키 관리

- AWS: Secrets Manager / Parameter Store
- 자체 구축: SOPS + age 또는 HashiCorp Vault
- `.env`는 **레포에 올리지 않음**, `.env.example`만 버전관리

## 5. 인프라 구성 (두 가지 옵션)

서비스 특성상 **옵션 B(하이브리드)**를 권장한다. 이유는 아래 비교 후 서술.

### 옵션 A — 풀 AWS

```
CloudFront ─▶ ALB ─▶ ECS Fargate (MAPI, AAPI, Worker)
                       │
                       ├─▶ RDS PostgreSQL (Multi-AZ)
                       ├─▶ ElastiCache Redis
                       └─▶ S3 + MediaConvert
```

- 장점: 완전 매니지드, 운영 부담 최소, Auto Scaling 쉬움
- 단점: 초기 비용 > 자체 구축, 한국 리전(ap-northeast-2) 의존

### 옵션 B — 하이브리드 (자체 Rocky Linux + AWS 관리형 일부)

```
[자체 온프레/IDC Rocky Linux 10]
  Nginx (TLS 종료)
   ├─ Docker Compose / Systemd
   │   ├─ MAPI (NestJS)
   │   ├─ AAPI (NestJS)
   │   └─ Worker (BullMQ)
   ├─ Redis 7 (컨테이너)
   └─ PostgreSQL 16 + PostGIS (컨테이너 또는 네이티브)

[AWS 관리형 활용]
  ├─ Route 53 (DNS)
  ├─ S3 (미디어)
  ├─ CloudFront (CDN)
  └─ SES (이메일)
```

- 장점: 초기 비용 최소화, Rocky Linux 활용, 트래픽 저렴
- 단점: DB 장애 복구·백업·모니터링을 직접 구성 필요 → **pgBackRest + WAL 아카이빙 + 주간 복구 리허설 필수**

### 옵션 C — 풀 자체 구축

Postgres, Redis, S3 호환(예: MinIO) 모두 자체. 초기 비용 최저이나, 미디어 트래픽이 붙을 때 대역폭/백업/가용성 리스크가 크다. **비권장 (MVP 이후 필요 시 전환)**

> **권장안**: MVP는 **옵션 B 하이브리드**로 시작 → 트래픽이 월 100만 요청, 저장소 1TB를 넘어가면 옵션 A로 이관 검토.

## 6. CI/CD 파이프라인 (GitHub Webhook 기반)

### 6.1 레포 구조 (모노레포)

```
waggle/
├── apps/
│   ├── mobile-api/          # MAPI (NestJS)
│   ├── admin-api/           # AAPI (NestJS)
│   ├── mobile-app/          # React Native
│   ├── admin-web/           # Next.js
│   └── worker/              # BullMQ 워커
├── packages/
│   ├── domain/              # 순수 도메인 (미션 검증, 포인트 계산 등)
│   ├── prisma/              # schema.prisma + migrations + 생성된 클라이언트
│   ├── dto/                 # 공용 Zod/DTO
│   ├── config/              # 공용 env 로더
│   └── ui/                  # 관리자·웹 공용 컴포넌트(ShadCN 확장)
├── infra/
│   ├── docker/              # Dockerfile per app
│   ├── compose/             # docker-compose (dev, stage)
│   ├── deploy/              # 서버 배포 스크립트 (webhook receiver)
│   └── nginx/               # Nginx 설정 템플릿
├── .github/
│   └── workflows/           # CI
├── pnpm-workspace.yaml
├── turbo.json               # Turborepo 캐싱
└── tsconfig.base.json
```

> **결정사항 4**: 패키지 매니저는 **pnpm**, 빌드 오케스트레이션은 **Turborepo**. React Native는 같은 워크스페이스에 두되 Metro가 워크스페이스 hoist를 잘 못 다루는 경우 `@react-native-community/cli` 대신 `expo` 또는 `nohoist` 처리.

### 6.2 CI (GitHub Actions)

```
PR 생성 → lint + typecheck + unit test
main 머지 → 이미지 빌드 + push (GHCR) → webhook 전송
```

워크플로 단계:

1. `pnpm install` (캐시)
2. `pnpm -r lint && pnpm -r typecheck`
3. `pnpm -r test` (영향받은 패키지만 Turborepo로)
4. `docker buildx build` (멀티 스테이지) → GHCR 푸시
5. 서버의 webhook receiver(`/deploy`)로 POST (HMAC 서명 검증)

### 6.3 CD (Webhook → Rocky Linux 서버)

서버 측 `deploy` 에이전트(간단한 Go/Node 바이너리 또는 `webhook` 오픈소스)가:

1. GitHub Webhook 수신 (`X-Hub-Signature-256` 검증)
2. `docker pull ghcr.io/waggle/mapi:<sha>`
3. `docker compose -f compose.prod.yml up -d --no-deps mapi`
4. 헬스체크(`/health`) 통과 후 이전 컨테이너 제거
5. 실패 시 롤백 (직전 태그로 재기동)

환경: **dev / staging / prod** 세 단계. `main` 머지 = staging 자동 배포. prod는 `release/*` 브랜치 수동 승인 후 태그 배포.

## 7. 확장성 / 장애 대응 고려사항

| 영역 | 고려사항 | 대응 |
|---|---|---|
| 산책 기록 동시성 | 동시 수천 명이 GPS 업로드 | 산책 세션은 클라이언트 버퍼링 → **산책 종료 시 일괄 업로드**. 중간 체크포인트는 5분 간격 압축 업로드 |
| 미션 자동 검증 | 산책 종료·교육 완료 시마다 조건 재계산 부담 | **이벤트 기반 처리**: `walk.completed`, `education.completed` 이벤트 → BullMQ로 비동기 검증 |
| 포인트 정합성 | 동시 적립/사용 경합 | PostgreSQL **트랜잭션 + SELECT ... FOR UPDATE** + 포인트 원장(point_ledger) append-only 테이블 |
| 영상 저장 | 교육 영상 용량 큼 | HLS(.m3u8) + 세그먼트 TS를 S3에 저장, CDN 캐시. 업로드는 presigned PUT |
| 푸시 알림 스파이크 | 예방접종 D-7 등 일괄 발송 | BullMQ `Queue.addBulk` + 레이트 리미터 (FCM 공식: 600 requests/min/project) |
| 관리자 데이터 유출 | 관리자 계정 탈취 | IP 화이트리스트 + 감사 로그(admin_audit_log) + 2FA(2차) |
